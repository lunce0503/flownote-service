# 실행 계획 (Exec Plans)

실행 계획은 일급 아티팩트다. 복잡한 작업의 진행 상황, 의사결정 로그, 기술 부채를 채팅이나 기억이 아니라 **버전 관리되는 문서**로 남겨, 에이전트와 사람이 외부 상황에 의존하지 않고 독립적으로 작업을 이어갈 수 있게 한다. 배경 원칙은 `docs/references/harness-engineering.md`, 계획 작성 기준은 `docs/PLANS.md`를 따른다.

## 디렉터리 구조

| 경로 | 역할 |
| --- | --- |
| `active/` | 진행 중인 실행 계획. 작업 재개 시 여기서 시작한다 |
| `completed/` | 완료된 계획 + 의사결정 로그. 왜 그렇게 했는지의 기록 |
| `tech-debt-tracker.md` | 알려진 기술 부채 추적기. 증상·영향·해소 조건을 명시 |

## 수명 주기

1. **생성**: 여러 하위 프로젝트·다단계 검증이 걸린 작업을 시작할 때 `active/YYYY-MM-DD-작업명.md`로 생성한다.
2. **갱신**: 단계 완료·의사결정·차질이 생길 때마다 같은 파일을 갱신한다. 대화가 끊겨도 이 파일만으로 재개 가능해야 한다.
3. **완료**: 작업이 끝나면 결과·검증·의사결정 로그를 채워 `completed/`로 옮긴다. 남은 부채는 `tech-debt-tracker.md`로 옮긴다.
4. **승격**: 반복될 지식은 계획에 두지 않는다 — 제품 행동은 `product-specs/`, 아키텍처 결정은 `design-docs/`, 품질 기준은 `QUALITY_SCORE.md`로 승격한다.

## 작성 요령 (계획 문서 필수 항목)

- **목표와 성공 기준**: 무엇이 되면 끝인지 검증 가능한 문장으로.
- **영향 범위**: 하위 프로젝트, 계약(API/타입/스키마), 배포 대상.
- **단계와 상태**: 체크리스트. 각 단계에 검증 명령을 붙인다.
- **의사결정 로그**: `결정 → 근거 → 대안과 기각 사유` 형식. 나중에 "왜?"에 답하는 부분.
- **명시적 가정과 제외 범위**: 하지 않기로 한 것을 적는다.
- **검증 결과**: 실행한 명령과 실제 출력 요약. "될 것이다"가 아니라 "됐다".

## 규칙

- 파일명은 `YYYY-MM-DD-작업명.md`.
- 비밀값·토큰·개인정보를 넣지 않는다.
- 오래된 계획은 삭제하지 않는다 — `completed/`로 옮기거나 정정 사유를 남긴다.
- 기술 부채는 단순 TODO가 아니라 **현재 증상 + 영향받는 흐름 + 해소 조건**으로 적는다.
