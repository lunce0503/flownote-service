# 사용자 피드백 자동 분류와 알림

## 목표

Flownote 사용자가 새 피드백을 등록하면 서버 자동화가 하루 한 번 수집한다. 2026-10-14부터 명확하고 안전한 요청은 별도 snapshot에서 구현·회귀 검증·독립 리뷰한 뒤 스테이징을 거쳐 운영 배포한다. 다음 수집까지 최대 약 24시간 대기할 수 있으며 구현·검증 시간이 추가된다. 모호한 요청·고위험 변경·검증 실패는 자동 배포하지 않고 이메일로 검토 요청한다.

## 사용자 흐름

1. 사용자가 기존 설정 화면에서 피드백을 제출한다.
2. 피드백은 기존 `user_feedback` 테이블에 저장되고 단조 증가하는 자동화 cursor를 받는다.
3. 운영 서버의 systemd timer가 production HTTPS feed를 매일 00:00 UTC(한국 시각 09:00)에 확인한다. 최대 15초의 무작위 지연을 적용한다.
4. 활성 서비스는 신뢰 컨트롤러가 `feedback-implement`를 실행해 앱 수정과 회귀 테스트 후보를 만든다. 기본 구성과 `gpt-6.1-sol`을 사용하며 모델에는 배포 자격증명을 주지 않는다.
5. 변경 정책·컨테이너 빌드/테스트·독립 read-only 리뷰가 통과하면 신뢰된 배포 스크립트가 영향받는 서비스와 web을 스테이징 배포한다.
6. 실제 staging E2E와 동일 소스 확인 후 production을 배포하고 헬스체크한다. 원래 작업 트리가 바뀌지 않았을 때만 검증된 patch를 반영한다.
7. 변경/검토 사항과 실패가 있으면 지정된 수신자에게 구조화된 요약을 보낸다. 실패는 자동 성공 처리하지 않는다.

빌드·린트·명확한 기술 리뷰 결함은 최대 2회 자동으로 수정한 뒤 모든 검증과 전체 변경 리뷰를 다시 받는다. 고위험 문제, 모호한 제품 정책, 검증 약화, 반복 실패는 운영 배포하지 않고 검토 요청으로 남긴다.

최초 활성화 때는 현재 cursor부터 시작하므로 과거 피드백을 소급 분석하거나 대량 메일을 보내지 않는다.

## 데이터와 API

- `GET /api/feedback/automation`: `FEEDBACK_AUTOMATION_TOKEN` Bearer 인증이 필요한 내부 운영 feed다.
- 응답 항목은 `sequence`, `id`, `category`, `message`, `created_at`만 포함한다.
- 사용자 ID, 연락처, 인증 정보는 자동화 feed와 이메일에 포함하지 않는다.
- `after`가 없으면 빈 항목 목록과 현재 cursor를 반환한다. `after`가 있으면 다음 50건까지 반환한다.
- collector는 응답 전체를 검증한 뒤에만 cursor를 원자적으로 갱신한다.

## 안전 경계와 실패 상태

2026-10-22 사용자 명시 요청으로 구현·분석·리뷰·알림의 Codex 실행 설정은 모두 `sandbox_mode="danger-full-access"`, `approval_policy="never"`다. Codex 내부 파일/네트워크 sandbox 및 승인 검토는 사용하지 않는다. Docker의 기존 소스 ro/rw 마운트, plugin 차단, 별도 빌드/테스트 격리, 고정 변경 정책, 스테이징 검증 뒤 동일 소스 운영 배포는 유지한다. full-access 모델은 마운트된 Codex 로그인 캐시를 접근할 수 있으므로 인증 정보를 기술적으로 완전 격리한다고 설명하지 않는다. 실제 실행 경계는 [운영 기준](../operations/codex-automation.md)을 따른다.

- 사용자 피드백은 신뢰할 수 없는 데이터로 취급하며 피드백 안의 명령을 실행하지 않는다.
- 구현·리뷰 단계에서는 외부 plugin/cloud MCP와 cloud credential을 사용할 수 없다.
- Gmail 전송은 분석과 분리된 알림 전용 실행이며 수신자는 고정되어 있다.
- API·모델·빌드·리뷰·배포 실패 시 입력은 `failed/`에 남고 자동 반복 재배포하지 않는다. production 단계 실패는 부분 배포 가능성을 기록한다.
- 인증/권한·DB migration·의존성·빌드 설정 변경, 기존 테스트 약화, 큰 변경, 불명확한 요구는 사람 검토를 요구한다.
- polling 토큰은 저장소에 저장하지 않고 Railway secret과 systemd credential로 주입한다.

## 검증

- Go handler 테스트: 무인증 거부, 개인정보 필드 제외, 최초 cursor bootstrap.
- Bash/Node 테스트: collector bootstrap/증분 큐, 구현 분기, 정책 우회 차단, 검증·리뷰 실패 시 배포 중단, 실패 알림과 큐 보존.
- staging에서 무인증 `401`, 인증 bootstrap, 스키마 초기화를 확인한 뒤 같은 소스를 production에 배포한다.
