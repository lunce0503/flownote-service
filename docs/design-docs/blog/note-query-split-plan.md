# 노트 메타 목록·본문 단건 조회 분리 계획

상태: 2026-10-19 isolated snapshot 구현 후보 작성. Go·cloud·채택 검증 대기. 작성: 2026-10-18.
운영에 반영한 계약·소비자·검증은 [Blog 코드맵](blog.md)과 [Markdown 실행 계획](../../exec-plan/completed/2026-10-19-blog-markdown-workspace.md)에서 추적한다. 아래 진단은 변경 전 근거다.

이전 통합 실행 상태는 [MVP 안정화 실행 계획](../../exec-plan/active/2026-10-18-mvp-stabilization.md)에서 관리한다.

## 문제와 근거

Go `notes.Repo.List`가 모든 노트의 S3/R2 본문을 순차 조회한다. 하나의 본문 조회 실패도 목록 전체 실패로 반환된다. 웹 BlockNote도 전체 목록을 요청한 뒤 ID를 찾아 상세 화면을 연다. 노트 수와 무관해야 할 단건 열기가 모든 본문 읽기에 의존한다.

## 목표와 범위

노트 목록에서는 본문 스토리지 읽기를 하지 않고, 노트 상세는 해당 노트 본문만 읽는다. 영향 대상은 Go Notes model/repo/handler, 웹 entities/blog·목록·편집기·동기화·충돌 재조회, 기존 API를 사용하는 Expo·Agent 등 소비자다. 기존 DTO와 본문이 필요한 호출부를 먼저 구분한다.

## 최소 구현과 호환성

1. 기존 `GET /api/notes`의 기본 응답은 바로 깨뜨리지 않는다. 메타 목록은 `GET /api/notes?view=summary&limit=50&cursor=...` 같은 명시적 선택 계약으로 추가한다. 정확한 파라미터·응답은 구현 시작 시 계약 테스트로 고정한다.
2. summary에는 ID, 제목, 생성·갱신 시각, revision, 필요한 목록 메타데이터만 반환한다. 본문 `content`를 빈 배열로 위장하지 않는다. 전용 NoteSummary 타입을 사용한다.
3. 사용자별 안정적 정렬과 최대 페이지 크기를 적용한다. 동률 정렬 키와 cursor를 검증하고 모든 페이지에 접근할 수 있게 한다.
4. `GET /api/notes/{noteId}`를 추가해 소유권을 확인한 노트 하나만 읽는다. 없는 노트·타 사용자 노트·본문 읽기 장애를 구분된 계약으로 처리한다.
5. 웹 목록을 summary로, 상세·저장 충돌 재조회·노트 단건 동기화를 detail로 이행한다. 모든 노트가 필요한 기능은 별도 호출로 유지하며 summary를 본문으로 취급하지 않는다.
6. 목록 미리보기를 위해 모든 본문을 다시 읽지 않는다. 별도 저장된 미리보기가 없다면 제목·시간 중심으로 표시하고, 검색 범위가 제목인지 본문인지 명확히 유지한다.
7. 기존 모바일·자동화 소비자의 응답 형태와 노트 생성·제목 변경·삭제·폴더 동작을 유지한다. legacy 전체 본문 목록 제거는 모든 소비자 이행이 검증된 후 별도 결정한다.

새 저장 테이블·검색 엔진·본문 인덱싱은 기본 범위가 아니다. 필요성이 입증되지 않으면 migration을 추가하지 않는다.

## 완료 기준과 검증

- 다수 노트의 summary 조회에서 object storage Get 호출이 0회다.
- 단건 조회에서 해당 노트의 본문만 최대 1회 읽는다. 다른 노트의 손상·지연으로 목록이나 정상 노트가 열리지 않는 일이 없다.
- 페이지 경계의 같은 생성 시각과 중복 cursor 요청에서 누락·중복 없이 탐색한다.
- 노트 목록의 생성·제목·삭제·폴더 이동과 편집기의 저장·재연결이 동작한다.
- 기존 `/api/notes` 소비자는 호환되며 사용자별 격리가 유지된다.

의미 있는 storage 호출 횟수·권한·페이지 계약 테스트를 Go에 추가한다. 명령은 `cd flownote-canvas && go test ./...`, `cd flownote && yarn verify`, 소비자 변경에 맞는 검사와 신규 staging E2E다. 고정된 합성 데이터로 요청 수·전송량·관찰 지연을 비교하고 측정하지 않은 성능 수치를 쓰지 않는다.
