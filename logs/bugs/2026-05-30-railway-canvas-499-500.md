# Railway canvas 499/500 investigation

## Symptom

- Railway production project: `flownote`
- Affected service: `flownote-main`
- Affected routes:
  - `GET /api/canvas/elements`
  - `POST /api/canvas/elements/save`
- Observed HTTP statuses:
  - `499`: client closed the request before the server sent a response.
  - `500`: server returned an error while handling canvas save.

## Evidence

- `railway logs --service flownote-main --http --status 499 --lines 100 --json`
  showed repeated 499s on canvas element load/save routes.
- Recent 499 save requests had large request bodies and long upstream durations:
  - about 455 KB to 710 KB request bodies
  - about 75 s to 195 s upstream durations
- `railway logs --service flownote-main --http --status ">=400" --since 2h --lines 120 --json`
  showed 500s on `POST /api/canvas/elements/save` before and between the 499s.
- `railway logs --service flownote-main --since 2h --filter "HikariPool" --json`
  showed repeated broken PostgreSQL connections:
  - `SQLSTATE(08006)`
  - `This connection has been closed. Possibly consider using a shorter maxLifetime value.`
- `railway logs --service flownote-main --since 2h --filter "I/O error occurred while sending to the backend" --json`
  showed repeated PostgreSQL driver I/O failures.
- `railway logs --service Postgres --since 2h --lines 200 --json`
  showed repeated Postgres container stops/starts and automatic recovery around the same times.

## Likely cause

The 500 errors are caused by `flownote-main` using PostgreSQL connections that were closed when the Railway Postgres container stopped/restarted. Canvas save then fails inside the Spring service with PostgreSQL I/O errors.

The 499 errors are the client-side consequence of the same incident pattern: canvas element load/save requests wait too long while the backend is blocked on or recovering from DB connection failures, then the browser/client aborts before Railway can return a response.

The slow path is amplified by large canvas save payloads and repeated concurrent save requests.

## Follow-up direction

- Disable sleeping/restarts for the Postgres dependency if it is configured to sleep.
- Tune Spring/Hikari connection lifecycle so stale Railway Postgres connections are recycled earlier.
- Reduce or debounce canvas save frequency and payload size so multiple large saves are not sent concurrently.

## 2026-05-30 mitigation

- The user disabled Railway serverless/sleep mode for Postgres.
- The web canvas autosave path now routes state changes through a single debounced save request instead of creating a new save timer in the canvas component for every render cycle.
- Manual save and page-hide flush cancel any pending debounced save before sending, which prevents a stale scheduled save from firing after an immediate save.
- The retry queue now keeps only the latest failed payload per canvas instead of accumulating multiple large save payloads for the same canvas.
- Line payloads are normalized before network save:
  - coordinates are rounded to one decimal place,
  - near-duplicate points are dropped,
  - points that are effectively collinear are removed.

## 2026-05-30 retry/deadlock follow-up

The latest Railway logs still showed client-visible retry conditions on the canvas routes after Postgres sleep mode was disabled.

Additional evidence:

- `POST /api/canvas/elements/save` returned repeated `499` responses around `2026-05-30T13:18:23Z` to `2026-05-30T13:20:54Z`, with some upstream durations reaching about 50 seconds.
- `GET /api/canvas/elements` returned repeated `499` responses around `2026-05-30T13:24:43Z`, with upstream durations around 91 to 93 seconds.
- `GET /api/canvas/metadata`, `GET /api/canvas/elements`, and `POST /api/canvas/elements/save` returned `500` responses around `2026-05-30T13:24:55Z` to `2026-05-30T13:26:57Z`.
- Runtime logs showed `org.postgresql.util.PSQLException: ERROR: deadlock detected` at `CanvasService.saveElements(CanvasService.java:198)`.
- Runtime logs also showed `HikariPool-1 - Connection is not available, request timed out after 10000ms (total=10, active=10, idle=0, waiting=1)`.

Updated cause:

- The current issue is no longer primarily Postgres sleep/restart.
- Concurrent canvas save requests for the same canvas can deadlock while updating canvas rows and element rows.
- Deadlocked or long-running requests consume all Hikari connections, causing other canvas reads/saves to wait and eventually fail.
- The client then remains in a long retry state or closes the request, which Railway records as `499`.

Code mitigation:

- Client save requests now use a 12 second timeout. When a save stalls, the client stops waiting and keeps only the newest canvas state for the next retry.
- The retry queue still stores one item per canvas, but each failed retry replaces its payload with the latest in-memory canvas payload when there are newer edits.
- Server `saveElements` now takes a transaction-scoped PostgreSQL advisory lock by user and canvas before mutating canvas elements. This serializes overlapping saves for the same canvas while still allowing different users/canvases to save independently.
