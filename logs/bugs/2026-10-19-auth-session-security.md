# 인증·세션 보안 보완

## 증상과 근거

첨부된 2026-10-18 인증 보고서의 F-01~F-06을 현재 소스에서 확인했다. 웹 로그아웃이 localStorage만 지우며 서버 세션을 폐기하지 않았고, Spring·Go의 양성 Redis 캐시가 세션 만료·폐기·역할 변경 후에도 접근을 허용할 수 있었다. 로그인 제한과 신규 비밀번호 필수값·길이 검증, 브라우저 보안 헤더도 부족했다.

## 수정

- 현재·전체 기기 로그아웃 API와 공유 legacy 캐시 삭제를 추가하고 세 서비스의 인증은 DB를 기준으로 변경했다.
- 공유 Redis 원자 카운터로 계정/전송 peer별 로그인 제한을 적용했다. Redis 장애 시 신규 로그인은 503이며 기존 인증은 DB로 계속 검증한다.
- 신규 비밀번호 필수값, 최소 15자, UTF-8 최대 72바이트, 기본 흔한/반복 암호 검증을 적용했다.
- 웹은 동일 출처 프록시와 HttpOnly·Secure·SameSite=Strict 쿠키를 사용한다. Origin과 custom header로 상태 변경을 검증하고 토큰을 브라우저 저장소나 로그인 JSON에 남기지 않는다.
- 웹 기본 보안 헤더와 강제 프레임 CSP, 나머지 출처 정책의 Report-Only를 추가했다.

## 검증 경계

staging 전용 계정으로 현재·전체 로그아웃, Spring·canvas·serve의 폐기 토큰 거부, 브라우저 쿠키·CSRF, 비밀번호 잘못된 입력, 로그인 429·Retry-After·복구와 기존 앱 E2E를 포함한 32개 시험을 통과했다. 같은 소스를 production에 배포했으며 운영은 비인증·정적 자산·화면 표시 read-only로 확인했다. production 계정이나 비밀번호·토큰 원문을 보고서에 기록하지 않는다.

## 스테이징에서 검출한 프록시 회귀

첫 클라우드 검증에서 태블릿 캔버스가 불러오는 상태에 머물렀다. 공개 GET 대조에서 Vercel `/web-api/socket.io/`는 404, `/web-api/socket.io`는 정상 Engine.IO 핸드셰이크였다. 두 웹 Socket.IO 클라이언트에 `addTrailingSlash: false`를 적용했다. 인증·로그아웃·로그인 제한 시험은 이미 통과했지만 실패한 gate를 production에 승격하지 않고 전체 검증을 다시 통과한 후 배포했다.
