# 게시글 전체 본문 조회로 인한 목록·단건 로딩 지연

## 증상과 확인 범위

게시글 접속이 느리다는 사용자 요청에 따라 현재 코드를 확인하고 staging 합성 계정의 목록 API를 측정했다. production 사용자 문서·본문·인증값은 읽지 않았다.

같은 환경에서 합성 노트/Canvas 각 5개를 번갈아 5회 조회했다. notes: 1062, 954, 1060, 814, 800ms / 33,348 bytes. Canvas 목록: 269, 138, 201, 129, 202ms / 770 bytes. 중앙값은 954ms 대 201ms다. 이는 API 목록 측정이며 브라우저 전체 로딩이나 동일 본문의 상세 성능 비교가 아니다.

## 원인과 추가 조사

- 확인: Go notes.Repo.List가 노트마다 object store Get을 순차 호출한다. 본문 읽기 하나 실패 시 전체 목록도 실패한다.
- 확인: BlockNote 상세·동기화·충돌 조회가 전체 목록을 읽은 뒤 ID를 찾는다.
- 가설: BlogWidget barrel의 목록/BlockNote 재수출이 무거운 편집기 청크 선행 다운로드를 유발할 수 있다. 실제 번들·브라우저 요청으로 확인한다.
- 별도 관측: 최초 staging 계정 생성 POST 502, 후속 공개 health/config 200, warm 합성 계정 측정 성공. 콜드스타트나 DB 장애를 원인으로 확정하지 않는다.

## 수정 방향과 검증

본문을 읽지 않는 summary 목록, 선택 노트만 읽는 detail, 지연 미리보기/레거시 편집기, 사용자별 캐시·요청 취소를 적용한다. Markdown 작업 공간으로의 전환과 동시에 기존 문서·초안을 보존한다. docs/design-docs/blog/markdown-workspace-plan.md와 실행 계획의 테스트·측정·staging-first 완료 기준을 따른다. 수정·배포 완료는 아직 아니다.

측정 artifact 최초 저장은 추가 도구 준비 중 ENOSPC로 실패해 stdout 관측값에서 복구했다. finally의 합성 문서 삭제 요청은 실행됐지만 결과 건수가 저장되지 않아 완전 정리를 확정하지 않는다. 이 작업에서 새로 받은 Go 이미지만 제거했으며 관련 없는 DB·이미지·업로드·캐시는 정리하지 않았다.
